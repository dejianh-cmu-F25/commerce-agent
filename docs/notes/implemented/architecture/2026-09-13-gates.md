# Agent Note: Guardrails are decision-only gates in one pipeline

Status: implemented (2026-09-13) — feature `020-gates`

## Problem

The architecture reserves `app/gates/` as the write guardrail pipeline (P3,
PB-2), but the checks were inline in tools: the cart tool tested provenance, the
order tools tested provenance and return eligibility. Guardrails scattered
across callers are easy to miss and hard to test in isolation.

## Alternatives considered

- **Leave the checks inline.** Works today, but every new write re-implements the
  rule, and there is no single place to review or extend (P3).
- **A generic framework (middleware, decorators, dependency injection).** More
  power than needed for two rules; it would obscure simple code (P6). Rejected.
- **A policy engine with configurable rules.** Over-built for this project.
- **Mutating gates that also perform the effect.** Convenient, but it hides side
  effects and duplicates the tool's ownership of outputs. Rejected.

## Decision

- **Gates are decision-only.** A `Gate` inspects a `GateContext` and returns a
  `GateResult` (allowed + reason); it never mutates the session or the store. The
  tool keeps ownership of side effects and of the exact output shape.
- **A shared context and a tiny pipeline.** `GateContext` carries the session and
  the few values gates need; `GatePipeline.run` returns the first block. No
  generic framework.
- **Two gates now:** `ProvenanceGate` (only server-issued ids; P4) and
  `ReturnEligibilityGate` (wraps the return policy; feature 014). The cart and
  order tools run them.
- **Behavior preserved.** Tools map a block to the identical JSON and status as
  before, so tests and evals are unchanged.

## Consequences

- New guardrails have one home and a testable shape; the tools stay thin.
- The exact user-facing error strings still live in the tools, so a gate's reason
  is internal unless the tool chooses to surface it (the return gate's reason is
  surfaced).
- Gates do not replace merchant approval: applying a staged change remains a
  human, web-endpoint action (P3), not a gate.
